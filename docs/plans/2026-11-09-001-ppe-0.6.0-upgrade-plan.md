# Upgrade CPEX to PPE 0.6.0

## Scope and evidence

Implement on the existing `feat/ppe_0.6.0` branch. At planning time, CPEX had workspace version `0.3.1` and pinned the crates.io `praxis-policy` facade, aliased as `ppe`, to `=0.5.0` with defaults disabled. The implementation and validation results are recorded below.

Reviewed the [PPE 0.6.0 release](https://github.com/praxis-proxy/policy/releases/tag/v0.6.0), published November 6, its [changelog](https://github.com/praxis-proxy/policy/blob/v0.6.0/CHANGELOG.md), and the [0.5.0–0.6.0 source comparison](https://github.com/praxis-proxy/policy/compare/v0.5.0...v0.6.0). The local upstream checkout is clean and matches the GitHub release tag:

- PPE 0.5.0: `d29a6a75f37a37fc9815d184ccf21564b2f4ac00`.
- PPE 0.6.0: `6b110aa9c400337b309426653886acf961f8f958`.

The recommendation is a stable RustCrypto upgrade with the existing builtin set. Keep FIPS and experimental Limitador enablement as separate work. New upstream capabilities must either have an explicit binding implementation or report that they are unsupported; generic serde is insufficient for several of them.

## Implementation decisions

### Identity input must have its own decoder

Add a shared CPEX host helper, used by `bindings/python/src/conversions.rs` and both identity decode paths in `crates/cpex-ffi/src/lib.rs`: `deserialize_payload(PAYLOAD_IDENTITY, ...)` and `cpex_invoke_resolved`.

Preserve the current caller shape (`source`, `source_header`, `headers`, `client_host`, `client_port`). Extract and validate headers separately, then populate PPE through `IdentityPayload::new` and `with_headers` / source/client builders. Do not restore serialization of PPE's secret inputs. Keep identity results sanitized by the existing `identity_result_value` helper.

Reject nonempty resolver-owned input fields before constructing the payload: subject, client, caller workload, delegation, raw credentials, resolution timestamp and raw claims. A DTO that simply ignores these would weaken the existing input guard. Keep malformed-input diagnostics free of header/token values.

Regression coverage must exercise real JWT identity through both Python and Go, including `InvokeResolved`, custom and multiple credential headers, missing credentials, forged resolver outputs, and result redaction. The Rust-only parity loop constructs identity payloads directly, so parity alone cannot detect this binding regression.

### Credential sources and live HTTP state need explicit handling

Map `Credential::Header` to the existing legacy-worker `source_header` contract. For cookie/query credentials, either introduce a worker DTO and negotiated feature that represents the location faithfully, or refuse the unsupported source with a clear host error. Never synthesize a header from a cookie/query parameter name. Match upstream non-exhaustive enums with a rejecting fallback.

In `crates/cpex-hosts-python/src/extensions.rs`, adapt `sanitize_http` and `returned_http` for `query` and `client_address`. Worker header edits may not overwrite the canonical query, client address, request line or secret-header provenance. A plugin without `read_query` must receive no live query. If worker query access is implemented, construct the granted value explicitly instead of relying on `HttpExtension::Serialize`, and negotiate worker support first.

Go should distinguish an absent query from an empty query, for example `Query *string`, because PPE distinguishes no query from a trailing `?`. `ClientAddress` should be host-supplied; PPE normalizes it on decode. Document that host callers must supply canonical HTTP fields from their trusted request context.

For separate Python/Go hook calls, reconstruct query from the original request or retain a dedicated live request context. Serialized `ModifiedExtensions` is a diagnostic/result representation for this field. Do not allow a `[REDACTED]` query returned by PPE to replace the original policy input. Preserve key bindings while reconstructing the remaining extension state.

### Request context must survive identity and downstream hooks

`cpex_invoke_resolved` currently invokes identity with `None` context and then passes the caller's original context to the downstream hook, discarding identity's table. Change it to pass the incoming table to identity and continue with identity's returned table. This is needed for PPE's within-request DPoP proof reuse and rate-limit stage marker.

Apply the same context threading to `examples/tutorial/src/mediate.rs` and `tests/parity/harness/src/engine.rs`, which currently pass `None` at each stage. Separate public calls should document that the returned context table belongs to the same request and must be passed onward; a new request gets a new table.

For a host offering rate limiting, the sequence is `ratelimit.pre_identity` before the first identity resolution, then `ratelimit.post_identity` after the last, then the governed invocation. Run each applicable stage once, including anonymous requests, and stop on a denial. Use PPE's HTTP payload/hook family. The upgrade's default feature set includes no limiter, so context plumbing does not require enabling Limitador. Low-level dispatch remains host-controlled; document its ordering obligation and make any automatic helper orchestration avoid double dispatch.

The Python decoder currently maps every non-CMF/non-identity hook to `GenericPayload`, and the FFI payload registry has no HTTP payload type. Exposing the rate-limit hooks to these callers therefore also requires typed HTTP payload construction or a dedicated orchestration helper; advertising the hook names alone does not provide working binding support. Until implemented, document the Rust-host support boundary.

Update `tests/parity/hook-renames.yaml`: `ratelimit.pre_identity` and `ratelimit.post_identity` must be represented in the hook inventory (explicitly unused in the existing legacy capture set if no fixture exercises them). Its current `unused: []` makes the registry-completeness check fail under 0.6.0.

### New nonserialized slots require a declared support boundary

Keep `llm_request` and acquired `metadata` intact in canonical Rust state and through `cow_copy`-based immutable merges. Reject worker attempts to replace them. Use `for_child_request()` when beginning a child policy invocation so acquired metadata does not inherit into a new invocation.

The current legacy SDK worker only advertises `credential`, `extensions`, and `cmf_hooks`; the host's `WORKER_KNOWN_CAPABILITIES` lacks `read_query`, `read_llm_request`, and `read_metadata`. For this upgrade, fail startup for a plugin explicitly requiring a new capability the installed worker cannot honor. Check the effective `read_all` view too: it must not become a route for accidental secret exposure. Supporting these fields fully requires feature negotiation and SDK changes outside this branch, followed by capability-filtered DTOs and immutable return handling.

For Python/Go callers, do not silently accept `llm_request` or `metadata` in the generic extensions map when PPE will ignore them. An LLM body/parts input can later be built explicitly into `LlmRequest` at the trusted host boundary. Metadata requires the acquired-facts installation API and provenance rules, not a plain deserialized map. Document the Rust support and binding limitations until those APIs exist.

### Config migration and release compatibility

Add `store: { kind: memory }` to `tests/parity/scenarios/elicitation-ciba/config.ppe.yaml` and `bindings/python/tests/test_builtins.py`'s generated CIBA config. Search maintained docs and all generated test/config strings for additional CIBA entries. Do not change the legacy `config.yaml` or retained baseline sources.

Move maintained JWT `header:` settings in tutorial policies, current parity configs and Go test YAML to `credential:`. Keep a deliberate legacy-header compatibility case. Check callers using bare tokens for non-Authorization resolvers: supply a matching `source_header` or an actual request header map instead of relying on the old broader fallback.

Recommend releasing as CPEX **0.4.0** because explicit CIBA storage and typed Go history alter user-facing contracts. Choose and apply the release version in release preparation, separately from the dependency investigation. A C ABI function signature need not change for the input-decoder fix. Review and test the MessagePack contract; if any existing payload contract becomes incompatible, bump `FFI_ABI_VERSION` and Go's expected version together so mixed artifacts fail clearly.

Keep PPE [#208](https://github.com/praxis-proxy/policy/issues/208) and [#209](https://github.com/praxis-proxy/policy/issues/209) as follow-ups. Both were still open on November 9. Retain binding builtin-install guards and the existing private-destination opt-in behavior and warnings. PPE 0.6.0 does not supply either requested fix.

## Implementation results

Implemented on `feat/ppe_0.6.0` in `24e1910` as CPEX 0.4.0, FFI ABI 4. The user selected RustCrypto and explicitly excluded FIPS support from this task. The workspace dependency supplies `crypto-rustcrypto` to every consumer; the feature graph contains no FIPS backend. No limiter was enabled.

Binding identity decoders restore private headers through PPE builders while retaining resolver-output guards and sanitized results. Fused FFI calls, the tutorial and parity thread request context. Go carries key bindings, raw query/client address and typed CMF history. Unsupported nonserialized inputs and worker capabilities fail clearly. Maintained JWT/CIBA configs and the hook inventory are migrated. Historical configs, snapshots and the baseline lockfile are unchanged.

The only added parity differences are the two malformed JWT credential code fields (`auth.malformed_header` → `auth.malformed_credential`), citing PPE #96. All 68 legacy requests, Valkey read-back and determinism ran successfully.

### Remaining release blocker

Three compatible security fixes are locked: `ctutils` 0.4.4, `rustls-webpki` 0.103.16 and `webpki-roots` 1.0.10. `make audit` still reports RUSTSEC-2026-0387 for `crypto-bigint` 0.5.5 through `biscuit-auth` 6.0.0 → `elliptic-curve` 0.13.8. The advisory's fixed version is 0.7.6, outside the published dependency requirement. No advisory suppression or incompatible override was added. Resolve this separately before release publication.

Native linking emitted macOS deployment-target warnings (15.2 objects linked for 15.0); verification passed. Release target CI was not triggered locally. No tags, push or publication were performed. The disposable Valkey and tutorial Keycloak containers were removed after validation.

### Biscuit follow-up and FIPS audit

On November 9, the user chose to retain crates.io-only dependencies and defer the Biscuit fix until upstream publishes it. The latest published `biscuit-auth` remains 6.0.0. Upstream [#349](https://github.com/eclipse-biscuit/biscuit-rust/pull/349), merged at `93832a82bf509ad81f05fdb6adaf69d03c56887b`, upgrades the RustCrypto stack but includes breaking crypto and RNG APIs. [#351](https://github.com/eclipse-biscuit/biscuit-rust/issues/351) tracks the release/backport request. No Git dependency, vendored crypto patch, downgrade or advisory waiver was added.

When a fixed release is available, update the dependency and lockfile, adapt the key API, verify interoperability with released 6.0.0 tokens, and run the Biscuit integration tests, dependency audit and package verification. RUSTSEC-2026-0387 remains a release blocker meanwhile.

The tracked source and current workspace feature graph contain no FIPS implementation, feature, configuration or runtime dependency. PPE selects only `crypto-rustcrypto`; neither OpenSSL libraries nor `aws-lc-fips-sys` are resolved. Remaining FIPS mentions document this support boundary. The `openssl rand` audit-doc example is a random-byte generation utility, not a FIPS dependency. The backend-neutral `PluginError::Crypto` handling remains required by PPE 0.6.0.
